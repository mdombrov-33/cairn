## What this is

A persistent-campaign TTRPG platform. One shared handcrafted world. Multiple campaigns set in that world — each with its own premise, location, conflict, and cast. Players pick a campaign, pick or create a character, and play inside that campaign until it concludes or they abandon it. An AI DM narrates scenes, voices NPCs, runs skill checks, tracks lore, and runs combat. State is fully persisted in Postgres — players resume exactly where they left off.

Stack: FastAPI + LangGraph + LangChain tools + LiteLLM + Postgres + SSE.

## Architecture

### Layering (hard rules)

```
api/v1/routes/    HTTP only — parse, call service, format response
domain/services/  Business logic — no FastAPI, no SQLAlchemy imports
db/queries/       All DB access — services and tools go through here only
tools/            Thin LLM-callable wrappers — call domain/services/, never own logic
agents/           One file per agent — agent_setup() + complete()/complete_with_tools()
llm/client.py     All LLM calls — no direct litellm imports anywhere else
prompts/          Versioned markdown + Jinja2 — load_prompt(name, version)
```

### Turn flow — non-combat

```
POST /sessions/{id}/turns
  → turns.service.prepare()
    → combat_active? → hardcode "combat_action", skip graph
    → else → turn_graph.run()
        ├── narrative_action → scene_narrator streams tokens
        ├── skill_check      → rules_lawyer → check_required SSE → [player rolls] → scene_narrator
        └── npc_dialogue     → scene_narrator with npc_context
  → turn_end SSE
  → lore_keeper fires async (fire-and-forget)
```

### Turn flow — combat

```
POST /sessions/{id}/turns  (combat_active = true)
  → combat_resolver tool loop (COMBAT_TOOLS)
  → enemy/ally turns via combat_ai (routes to enemy_ai or ally_ai prompt)
  → scene_narrator streams narrative
  → turn_end SSE
```

## Design decisions (locked)

**Handcrafted world + campaigns.** One shared world with rich lore (factions, geography, history, deities). Multiple campaigns set in different parts of that world — each handcrafted with its own premise, key NPCs, locations, and act structure. The LLM executes and improvises within that structure; it does not invent the structure. Critical Role DM model: the DM prepares a timeline of core events, everything that happens within them is improvised and roll-driven. LLM cannot maintain 50+ hours of coherent narrative without guidance — the act structure is that guidance.

**Campaign acts structure.** Each campaign is divided into acts. Each act has a central conflict and defined core events. The LLM moves through acts based on what actually happens in play. When the final act reaches narrative resolution (not a binary kill condition), the DM writes the epilogue and the campaign is marked complete.

**Campaign isolation + world echoes.** Campaigns are isolated — one player's story does not affect another's live campaign. When a campaign concludes, LoreKeeper writes a `CAMPAIGN_CONCLUDED` world bible entry. Future campaigns in the same world can retrieve this as historical lore. Async, not real-time.

**Sessions are technical, not user-facing.** From the player's perspective, you open the game and resume exactly where you left off. Sessions exist as LangGraph thread checkpoints. *(Caveat: code currently exposes `POST /sessions/{id}/end` — must be reconciled in Slice 5.)*

**Scene summaries handle context compression. No session summarizer service.** When a scene ends, its summary is written to `Scene.summary`. The DM receives current act context + current scene summary + last N turns within the scene. World bible captures all meaningful facts via LoreKeeper.

**3–4 premade characters per campaign.** Each campaign ships with premade characters whose bio and motivations are written to fit the specific campaign context.

**Custom character onboarding via intro scene.** If a player creates their own character, the DM runs a short 2–3 turn intro scene before the main campaign begins. DM knows the campaign context and the character's class/background and improvises a placement scene.

**Ability scores use standard array only.** Client submits six scores; backend validates they equal `[15, 14, 13, 12, 10, 8]` sorted.

**Backend derives all character stats from SRD.** On creation client sends only choices (race, class, background, ability scores, skill choices, AC, name, alignment, bio, personality, optional voice traits/subclass/is_companion). Backend derives everything else.

**One character per campaign run.** Played until campaign concludes or character dies. Abandoning is a clean stop.

**Companions (`is_companion: True`) are AI-controlled — locked.** Full character sheets, viewable by the player, AI-controlled in combat. In narrative turns the DM and `dialogue` agent give them voice and presence. Player does not directly control them.

**Party model — Characters vs NPCs:**
- `Character` (`is_companion=False`) — player's PC. Full sheet, player-controlled.
- `Character` (`is_companion=True`) — companion/sidekick. Full sheet, AI-controlled.
- `NPC` — all world entities: enemies, merchants, quest givers, allies. DM/AI-controlled.
- Combat ally — an NPC temporarily fighting for the party (`role="ally"`).

**Character death is a state, not a delete.** `is_dead: bool` on Character. `DELETE /characters/{id}` is mistake cleanup only.

**System-computes-facts.** `CombatResolver` produces typed outcome; `SceneNarrator` prose-renders from it. The LLM narrates facts, never owns them.

**Turn events log.** Every mutation calls `_emit(db, event)`. Makes evals tractable: score against event sequences.

**Tools are thin wrappers.** Business logic in `domain/services/`. No game logic in `tools/`.

**SRD is the source of truth for rules.** Features are string names; the LLM queries SRD lookup tools at runtime.

**Reactions are system-detected, not LLM-detected.** Reaction bus fires deterministically. Implementation in Slice 6.

**Action economy is tool-enforced, not LLM-enforced.** `use_action`, `use_bonus_action`, `use_reaction`, `spend_movement` tools track usage.

## Conventions

- **NOT NULL columns with defaults** — always add `server_default` alongside `default`. Alembic only picks up `server_default`. Integers: `server_default="8"`. JSONB lists: `server_default="[]"`. JSONB dicts: `server_default="{}"`.
- **Migrations** — always Alembic-generated (`make revision`). No hand-written SQL.
- **Package management** — always `uv add`. Never edit `pyproject.toml` by hand.
- **Prompt versioning** — every agent has a versioned markdown prompt in `prompts/{name}/v1.md` with frontmatter (`temperature`, `version`). Loaded via `load_prompt(name, version)`. Active version overridable per-environment via `LLM_PROMPT_VERSIONS` env var.
- **Tool pattern** — `@tool` decorator, `Annotated[type, "description"]` per param, `await tool.ainvoke({"arg": val})` at call sites. Never `.coroutine()`.

### Slice 1 — Character CRUD + schema cleanup - DONE

*Depends on: nothing (Phase 0 schema work is already merged).*

Bring the character contract in line with the locked design. The current schemas predate the "backend derives everything" decision and contain heavy drift.

**Decide first:**
- `is_dead: bool` vs `status: active | dead | abandoned` enum. Currently abandoned campaigns leave the character in limbo — `is_dead=False` but never returned to. An enum is cleaner; a bool is one fewer field. Pick one before the schema rewrite.
- Field naming: keep model field `stats` or rename to `ability_scores`? `stats` is what the DB column is called; `ability_scores` is what the design doc says. Decide whether to align the schema layer to the design name (with a serialization alias) or accept divergence.
- `TurnResponse.events`: expose the typed event log to clients or keep it internal? Frontend combat tracker (Slice 11) will need it; if so, add now.

**Build:**
- `POST /v1/campaigns/{cid}/characters` — derive all stats from SRD. Client sends:
  - **Required for everyone:** `name`, `race`, `character_class`, `background`, `ability_scores` (validated as standard array `[15,14,13,12,10,8]`), `skill_choices` (from class proficiency options), `ac`, `alignment`, `bio`, `personality`.
  - **Required if `is_companion=True`:** `voice_traits` (used by `dialogue` and `ally_ai` for non-combat and combat respectively).
  - **Optional:** `subclass` (most classes choose at level 2–3, required at level-up when timing demands it), `is_companion` (default `False`).
  - **Backend derives:** `hit_die_size` (`classes.json`), `max_hp`/`hp` (hit die + CON mod at level 1), `saving_throw_proficiencies` (class), `spellcasting_ability` (class), `spell_slots` (`class_levels.json` at level 1), `features` (class level-1 features + race traits), `tool_proficiencies` (background), `skill_proficiencies` (background fixed + player choices), `speed` (race — dwarves 25, most 30), `proficiency_bonus` (always 2), `initiative` (DEX mod), `passive_perception`.
  - **Inventory:** fixed items from `classes.json[class].starting_equipment` auto-added; equipment options skipped for now.
- `GET /v1/campaigns/{cid}/characters` — list full party (player character + companions).
- `PATCH /v1/campaigns/{cid}/characters/{ch}` — `name` and `bio` only, player characters only (`is_companion=False`).
- `DELETE /v1/campaigns/{cid}/characters/{ch}` — hard delete, mistake cleanup.

**Fix:**
- **`CharacterCreate` schema is wildly out of date** — accepts `hp`, `max_hp`, `level`, `saving_throw_proficiencies`, `spell_slots`, `spells_known`, `features`, `currency` from the client (we said backend derives). `alignment`, `bio`, `personality` are optional (we said required). Has `skill_proficiencies: list[str]` (already-derived); plan introduces `skill_choices`. `features: list[str]` while model has `list[Any]` of dicts. Full rewrite.
- **`CreatureBase` is missing fields added in Phase 0** — no `tool_proficiencies`, `feats`, `is_dead`, `hit_die_size`, `hit_dice_remaining`, `resources`, `concentration`, `death_save_successes`/`failures`. GET responses are missing fields. Update.
- **`CharacterResponse`** — confirm it inherits the updated `CreatureBase` and adds `is_dead` for completeness.
- **`character_to_dict` in `tools/game_state.py` is missing the same Phase-0 fields** — the dict the LLM sees via game state tools doesn't include `tool_proficiencies`, `feats`, `is_dead`, `hit_die_size`, `hit_dice_remaining`. Same drift as `CreatureBase` but on the agent-facing side. Update alongside `CreatureBase`.
- **No campaign-level character list query** — `db/queries/characters.py` has `get_character_by_campaign` which filters to `is_companion=False`. Add `list_characters_by_campaign(campaign_id)` returning all.
- **Ownership check pattern** — currently `get_character_by_campaign` doesn't take `owner_id`. Route service does `get_campaign_owned_by` first. Verify the same pattern in DELETE/PATCH and add an explicit `assert_owns_character` helper if useful.

**Open follow-ups:**
- Variant Human feat at level 1 — SRD doesn't include it. Defer.
- Multiclassing — intentionally not supported in v1.
- Spell selection at creation — wizards learn 6 spells at level 1, clerics prepare from full list. The `skill_choices` pattern needs a parallel `spell_choices` field for spellcasters. Decide in this slice or defer to Slice 4 (level-up flow already needs it).

**Verify:** POST a fighter with standard array → HP = 10 + CON mod, saving throws match class, proficiency bonus = 2. GET returns full party including companions. PATCH bio works. ### Slice 2.5 — Equipment + AC derivation + feat completeness - DONE

*Depends on: Slice 2.*

Caught while building Slice 2. `ac` is currently sent by the client at character creation as a flat int. AC in 5e is `armor base + DEX (capped by armor type) + shield + feat/magic bonuses + unarmored defense`. Treating it as client input means every feat handler that "bumps AC" (Defense fighting style, Dual Wielder, Shield Master) is just nudging a magic number with no relationship to what the character is actually wearing. Several other feat handlers shipped in Slice 2 also drop their grants on the floor because the underlying tracking doesn't exist (armor proficiencies, weapon proficiencies, Battle Master maneuvers). The AC fix and the feat-completeness fix share the same root: we have no equipment system. This slice builds the minimal one and then fixes the feats that depend on it.

**What's actually broken right now (caught during Slice 2 audit):**
- `ac` is client-input on `CharacterCreate`, not derived from equipment.
- No `armor_proficiencies` or `weapon_proficiencies` columns. Class data lists them in SRD; we ignore that data at creation.
- `defense` feat handler does `char.ac += 1` unconditionally. Doesn't check armor is equipped, doesn't ever come off if armor is removed. Currently unreachable via level-up (fighting-style type rejected at ASI), but still wrong.
- `tough` handler applies `+2 × current_level` once when taken. RAW: also gain +2 max HP for every level gained *after* taking it. `apply_level_up` doesn't read the feat list and apply this scaling.
- `heavily-armored` / `lightly-armored` / `moderately-armored` / `heavy-armor-master`: bump the ability score (correct) but drop the armor-proficiency grant entirely. Without the proficiency, the +1 STR/DEX is half the feat.
- `weapon-master`: same — +1 STR/DEX kept, "4 weapon proficiencies" dropped.
- `heavy-armor-master`: also drops "reduce 3 damage from non-magical bludgeoning/piercing/slashing while wearing heavy armor."
- `martial-adept`: grants 1 superiority die (correct) but drops "learn 2 maneuvers" — we don't track maneuvers anywhere.
- `magic-initiate`: appends 3 spells to `spells_known` but doesn't track the "cast the 1st-level spell once per long rest without using a slot" — should be a resource.
- `skilled`: appends 3 picks to `skill_proficiencies` but the feat says "skills *or* tools (player picks per pick)". Tools should land in `tool_proficiencies`.
- `observant`: +5 passive Perception (correct) but drops the +5 passive Investigation (we don't track that field).

**What's actually correct (audited against PHB):**
- `alert`, `mobile`, `keen-mind`, `actor`, `athlete`, `tavern-brawler`, `resilient`, `lucky`, `spell-sniper`. Their state-mutating effects are all in. Behavioral parts (Mobile's no-OA-after-attacking, Lucky's spend mechanics, Alert's surprise immunity) are deliberately LLM-narrated.

**Equipment slot philosophy — no new tables.** D&D 5e has a small number of mechanically-meaningful gear positions: armor (body), shield (held), main-hand weapon, off-hand weapon (mutually exclusive with shield). Rings, amulets, cloaks, boots, etc. are magic-item flavor — the LLM reads the item description and applies the effect when narratively relevant. We do **not** add a `slots` table or 10-slot character UI. The existing `inventory: list[dict]` already has `equipped: bool` per item. Constraint logic ("only one armor equipped at a time", "shield and off-hand weapon are mutually exclusive") lives in an `equip()` service that flips flags. AC is derived from the filtered `equipped=True` items.

**AC derivation formula:**
```
equipped_armor   = first(equipped where SRD type == armor)
equipped_shield  = first(equipped where SRD type == shield)
dex_mod          = mod(ability_scores.dex)

if no armor:
    base = unarmored_ac(char)         # default 10+DEX
                                       # barbarian: 10+DEX+CON
                                       # monk: 10+DEX+WIS
else:
    armor_data = SRD lookup
    base = armor_data.base_ac + min(dex_mod, armor_data.max_dex_bonus or ∞)

ac = base + (2 if shield else 0) + feat_ac_bonus(char) + magic_item_bonus(char)
```

**Build (equipment system):**
- Add `armor_proficiencies: Mapped[list[str]]` JSONB column on `Character` (and `NPC` for parity).
- Add `weapon_proficiencies: Mapped[list[str]]` JSONB column on `Character` (and `NPC`).
- Alembic migration for both columns.
- `services/equipment.py`:
  - `equip(char, item_name)` — flips matching inventory item to `equipped=True`. Enforces: only one armor equipped, only one shield, shield + off-hand weapon mutually exclusive.
  - `unequip(char, item_name)` — flips back.
  - `is_armor(item_name) -> bool`, `is_shield(item_name) -> bool`, `is_weapon(item_name) -> bool` — SRD lookups.
- Add SRD helper: `get_armor(name)` returning base AC, max DEX bonus, armor category (light/medium/heavy/shield), STR requirement.

**Build (AC derivation):**
- `services/ac.py` (or fold into `characters.py`):
  - `derive_ac(char) -> int` — implements the formula above, including unarmored defense for barbarian and monk.
  - `feat_ac_bonus(char) -> int` — sums per-feat AC contributions: Defense (+1 if armor equipped), Dual Wielder (+1 if dual-wielding), Shield Master / Medium Armor Master (none directly to AC), magic items if any.
- Extend `recompute_derived_stats(char)` to recompute AC after any mutation that could change it (equip/unequip, ASI to DEX, feat granting AC bonus).

**Build (proficiency wiring at creation):**
- `services/characters.create`:
  - Read `cls_data["proficiencies"]` from SRD. Filter into armor profs, weapon profs, save profs. Currently only saves are stored.
  - Set `armor_proficiencies` and `weapon_proficiencies` from class data.
  - Auto-equip class starting equipment: flip `equipped=True` on the armor and primary weapon from `starting_equipment`. Compute AC.
  - Race may grant weapon proficiencies (elf longsword, dwarf battleaxe). Apply.

**Fix:**
- **Nuke `ac` from `CharacterCreate`.** Remove the field entirely. Update the schema, the route, the test fixtures, and the integration tests that send it.
- **`defense` handler:** stop mutating `char.ac` directly. The +1 is now expressed in `feat_ac_bonus(char)` only when armor is equipped. Re-derives correctly when armor comes off.
- **`tough` handler scaling:** in `apply_level_up`, after computing HP gain, check `if "tough" in feat indices: max_hp += 2; hp += 2`. Retroactive on take is already correct; this adds the going-forward part.
- **Armor-proficiency feats** (`heavily-armored`, `lightly-armored`, `moderately-armored`, `heavy-armor-master`): each handler now appends the appropriate category to `char.armor_proficiencies` in addition to the ability bump. `lightly-armored → "light"`. `moderately-armored → "medium"` + `"shields"`. `heavily-armored / heavy-armor-master → "heavy"`.
- **`weapon-master`:** add `options.weapons: list[str]` of length 4. Append to `char.weapon_proficiencies`. Validate against SRD weapon list.
- **`heavy-armor-master`:** in addition to +1 STR and heavy armor proficiency, expose a flag (e.g. `feats` entry options carries a `damage_reduction: 3` marker, or compute from feat presence in damage tool). Damage tool checks if attacker's damage type ∈ {bludgeoning, piercing, slashing}, attacker's weapon is non-magical, character has heavy armor equipped, and reduces by 3.
- **`skilled`:** change `options.skills: list[str]` to `options.picks: list[{type: "skill"|"tool", name: str}]` length 3. Skills go to `skill_proficiencies`, tools to `tool_proficiencies`.
- **`martial-adept`:** add `options.maneuvers: list[str]` of length 2. Track in a new `maneuvers` JSONB list field on Character (or as a sub-list on the feat entry — decide). LLM reads at runtime.
- **`magic-initiate`:** add a `magic_initiate_free_cast: {current: 1, max: 1, resets_on: long_rest}` resource. Or: extend feat options with which spell is the 1st-level slot, and the resource auto-derives. Decide implementation.
- **`observant`:** leave `passive_perception` +5 logic in `recompute_derived_stats`. Add a `passive_investigation` field on Character or compute on demand. Decide.

**Decide:**
- **AC derivation: recompute on every read or only on mutation?** `derive_ac` is cheap (handful of dict lookups + arithmetic), but if we recompute on read we never have stale AC. If we cache, we need to call recompute from every mutation surface (equip, unequip, ASI to DEX, feat, magic item, take/lose proficiency). Lean toward recompute-on-read with the value cached on `char.ac` for the API response, recomputed in `recompute_derived_stats` after every mutation surface. Same pattern we already use for initiative and passive_perception.
- **Equip/unequip route now or in Slice 11?** The service must exist for AC derivation to work. The HTTP route can wait. Default: service this slice, route in Slice 11.
- **Maneuvers storage:** new `maneuvers: list[str]` column on Character vs. nest in feat options (`feats[i].options.maneuvers`). Column is queryable; nested is no-migration. Lean nested.
- **`passive_investigation`:** add as a stored derived stat or compute on demand from skill profs + WIS + observant feat. Lean compute-on-demand in a getter; not stored. Avoids another column for one feat.
- **Magic Initiate free-cast resource:** real resource (rests on long rest, decremented by tool) vs. ignore (LLM tracks narratively). Lean real resource — it's mechanical, deterministic, and the system already has resource plumbing.
- **NPCs:** do NPCs also get derived AC? They have `ac: int` set at creation/spawn. Most NPCs are statblock-driven — their AC comes straight from the SRD monster entry. Probably leave NPC AC as-is (statblock value), only derive for Characters. Confirm.

### Advanced combat mechanics

- **Readied actions** — "I ready an action to shoot if the door opens." Requires `readied_action: {action, trigger, combatant_id}` on combat state.
- **Legendary actions / legendary resistance / lair actions** — boss monster mechanics. Legendary actions happen at end of other creatures' turns; lair actions on initiative count 20. Needs post-turn hooks.
- **Summoned creature tracking** — Conjure Animals, Find Familiar, Unseen Servant. Temporary combatants linked to a summoner.
- **Wild Shape / Polymorph** — completely replaces the creature's stat block. Needs `transformed_into: {stat_block}` field.
- **Two-weapon fighting** — bonus attack when wielding two light weapons. Needs equipped weapon awareness.
- **Grapple / Shove** — special attack actions using contested Athletics. `resolve_contest` covers the mechanic; LLM needs prompting to use it.
- **Cover mechanics in attacks** — half cover (+2 AC), three-quarters (+5 AC), total (untargetable). Currently ignored even though `Locations.zones` has the data.
- **Darkness and invisibility** — disadvantage vs unseen targets. `conditions` handles "blinded" but not spatial visibility.

### Game systems

- **Faction reputation** — factions exist in lore, no mechanical standing yet. Numerical reputation for social checks, access, pricing.
- **Economy** — currency exists on Character (`gp/sp/cp`); no shops, prices, transactions enforced.
- **Crafting** — out of scope.
- **Time tracking** — in-game days, seasons, weather, environmental effects — out of scope.

### Platform features

- **Portrait generation** — deferred. Blocked on Replicate or Bedrock image gen integration. `portrait_url` field exists.
- **True multiplayer** — players in the same campaign with shared live consequences. Architecturally possible but not designed. World echoes (Slice 5) are the v1 substitute.
- **Mobile client** — out of scope.

### Test coverage

- Unit tests for turn graph nodes — `tests/conftest.py` patches the entire graph at module level. Adding granular agent tests is worth doing post-launch.
- Load testing — none planned for v1.
